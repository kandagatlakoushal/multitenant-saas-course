Four kinds of isolation test

 LEAK          tenants A and B with the SAME business keys -> each sees only its own data
 FORGED HEADER log in as A, send X-Tenant-Id: B            -> 400, nothing of B
 MISSING       no tenant on message/request                -> DLQ / 4xx, nothing written
 CONCURRENCY   1-thread pool, alternate A,B,A,B            -> context never stale

Use real PostgreSQL (Testcontainers), not H2. The point is PostgreSQL's real search_path, RLS and temp-table behaviour.

@Test
void sameBusinessKeyInTwoTenantsNeverCrosses() {
    as("acme",  () -> trades.save(new Trade("10001", "ACME-DATA")));
    as("hooli", () -> trades.save(new Trade("10001", "HOOLI-DATA")));
    assertThat(as("acme",  () -> trades.findByAccountNo("10001"))).extracting(Trade::payload).containsExactly("ACME-DATA");
    assertThat(as("hooli", () -> trades.findByAccountNo("10001"))).extracting(Trade::payload).containsExactly("HOOLI-DATA");
}

@Test
void asyncWorkSeesSubmittersTenant() throws Exception {
    ThreadPoolTaskExecutor ex = new ThreadPoolTaskExecutor();
    ex.setCorePoolSize(1); ex.setMaxPoolSize(1);          // force reuse every time
    ex.setTaskDecorator(new TenantTaskDecorator()); ex.initialize();
    for (String t : List.of("acme", "hooli", "acme", "hooli"))
        assertThat(as(t, () -> ex.submit(TenantContext::require).get())).isEqualTo(t);
}

Capstone (60 min)

Part A (35 min): conversion checklist. For each service, cover the boundary, propagation in and out, data access, shared state, config, flag and conditions, failure behaviour, and observability.

  1. Parser: stateless. Consumes PARSE.*, publishes ENRICH.*. Uses @Value("${customer.date-format}").
  2. Enricher: REST calls to reference data; an instrument cache keyed by ISIN; a @Scheduled counterparty reload; CompletableFuture for two parallel calls.
  3. UI gateway: OIDC login, calls the reporter, reads X-Customer from the browser for an admin view.

Part B (25 min): 10 isolation tests. For each: name, setup, action, expected result, and the leak it catches.

Worked answer: Part A

Common (the starter provides): a typed boolean flag with class-level conditions; TenantContext plus MDC; a validated registry accepting only ACTIVE tenants; routing (no default target, not lenient) feeding the switch-on-borrow wrapper; a registered context accessor and task decorator; client customizers plus ArchUnit; a MeterFilter allow-list.

Parser: listeners registered from the registry; requireKnown, set, clear in finally; destination(stage, tenant) and copy tenantId on send; group ID tenantId:accountNo; date format from TenantSettings with a per-tenant formatter cache; unknown tenant or parse error throws, retries a few times, goes to the DLQ with its tenantId; messages and errors metrics by tenant.

Enricher: the same boundary; the reference-data client built from the builder; CompletableFuture given a propagating executor (or made sequential); cache key (tenant, isin) with the loader setting the context from the key; the scheduler loops over tenants with one transaction each and keeps old data on failure; reference-data 4xx goes to the DLQ, 5xx retries, and there is never a fallback to another tenant's data.

Gateway: remove X-Customer (client tenant headers get 400 and a metric); TenantResolutionFilter after authentication, not a bean; admin switching by allow-list, audited and stored in the session; outbound header through the builder; tenant-scoped lookups returning 404; a per-tenant rate limit returning 429.
