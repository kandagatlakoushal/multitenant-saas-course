Settings frozen at startup

A singleton holds one value. In a shared JVM, one value cannot be right for every tenant. Ask of every setting: "Could two tenants want different values?" If yes, it must become a run-time lookup.

Frozen patternWhy it's wrong when shared
@Value("${customer.x}") on a singleton fieldRead once; holds one value
@ConfigurationProperties("customer")Also bound once at startup
Constructor or @PostConstruct loading "the customer's" dataRuns once, with no tenant in context
@Profile("acme") beansThe bean set is fixed for all tenants
static fields built from configJVM-wide, for the JVM's whole lifetime
public record TenantSettings(String baseCurrency, ZoneId zone, int settlementLagDays) {}

public TenantSettings forCurrent() {
    String t = TenantContext.require();
    TenantSettings s = byTenant.get(t);
    if (s == null) throw new UnknownTenantException(t);   // fail closed, no defaults
    return s;
}

Switching old and new behaviour in a starter

 my-mt-starter.jar
   META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
       com.example.mt.MultiTenancyAutoConfiguration   (@AutoConfiguration,
                                                        @ConditionalOnProperty(... havingValue="true"))
 service:
   LegacyParseListener  @ConditionalOnProperty(havingValue="false", matchIfMissing=true)  -> default ON
   ShardParseListener   @ConditionalOnProperty(havingValue="true")                         -> opt-in
  • havingValue set: matches when the property equals it. Spring Boot compares case-insensitively.
  • havingValue not set: matches when the property is present and not false.
  • matchIfMissing (default false) decides the absent case. true on the legacy class is the opt-in flag's safe default.

The trap: @Conditional annotations only work on component classes and @Bean methods. JmsListenerAnnotationBeanPostProcessor registers every @JmsListener method on an existing bean without evaluating conditions. So a condition on a listener method is silently ignored. Put it on the class. Spring Boot: Creating your own auto-configuration; @Conditional javadoc.

Practice (12 min)

Code review: find three frozen settings, and one that's fine

@Service
public class SettlementDateCalculator {
    @Value("${pipeline.batch-size:500}") private int batchSize;
    @Value("${customer.settlement-lag-days}") private int lagDays;
    private final HolidayCalendar calendar;
    private static final ZoneId ZONE = ZoneId.of(System.getProperty("customer.zone", "Europe/London"));

    public SettlementDateCalculator(HolidayCalendarLoader loader) { this.calendar = loader.load(); }

    public LocalDate settle(Instant t) {
        return calendar.addBusinessDays(t.atZone(ZONE).toLocalDate(), lagDays);
    }
}
Worked answer
  • Fine: pipeline.batch-size is a platform setting.
  • Frozen 1: lagDays. Replace with settings.forCurrent().settlementLagDays().
  • Frozen 2: loader.load() in the constructor runs with no tenant. Replace with a provider: calendars.forCurrentTenant(), cached with a tenant-scoped key.
  • Frozen 3: static final ZONE. Replace with settings.forCurrent().zone().
