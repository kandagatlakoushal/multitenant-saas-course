Switch on every borrow

Your win: write the data-source wrapper that sets the tenant on every connection borrow, combine it with routing, and check that the connection numbers add up.

Recall first (2 min)

  1. Which survives returning a connection to the pool: SET or SET LOCAL?
  2. A tenant's schema doesn't exist and the path includes public. What happens?
Check
  1. SET (session scope). SET LOCAL ends with the transaction. (Lesson 5)
  2. The query silently reads public: a leak.

Why every borrow

 pool --> borrow [conn: path=t_acme] --> hooli's query --> return [path=t_acme]
          (left by the last user)        reads t_acme       Hikari doesn't reset SQL-level SET
  • HikariCP's connectionInitSql runs once per physical connection, not per borrow.
  • Hikari resets state changed through the JDBC API (auto-commit, isolation, read-only, catalog, schema) when a connection returns. It cannot know about a SET you ran as SQL. ⚠ verify the exact reset list for your version

HikariCP README.

public class TenantSchemaDataSource extends DelegatingDataSource {
    @Override
    public Connection getConnection() throws SQLException {
        String schema = registry.requireSchemaFor(TenantContext.require());   // validated, fail closed
        Connection c = super.getConnection();
        try (PreparedStatement ps = c.prepareStatement("SELECT set_config('search_path', ?, false)")) {
            ps.setString(1, schema);                                           // tenant schema only, no public
            ps.execute();
        } catch (SQLException e) { c.close(); throw e; }
        return c;
    }
}

This runs before Spring starts the transaction (the transaction manager turns off auto-commit after getting the connection). So a rollback cannot undo the SET. Alternative: c.setSchema(schema), which Hikari tracks and resets on return. ⚠ verify how pgJDBC implements setSchema. For RLS, set app.tenant_id the same way.

Routing between databases

 getConnection()
   -> TenantRoutingDataSource           which DATABASE, by registry placement
        "shared-1"  -> TenantSchemaDataSource -> Hikari(shared-1)   SET path per borrow
        "db_globex" -> Hikari(globex)                               no switch needed

AbstractRoutingDataSource falls back to its default target when the key is null, or when the key is unknown and lenientFallback is true (the default). That is a default tenant by another name. Don't set a default target, and call setLenientFallback(false). Javadoc.

Connection arithmetic

connections to one server = pods × pools on that server × maximumPoolSize. PostgreSQL's default max_connections is 100. Keep pools small (see the pool sizing wiki), or give database-per-tenant tenants their own servers. With PgBouncer in transaction mode, a session SET can leak between clients ⚠ check the PgBouncer docs.

Migrations across hundreds of schemas

Run Liquibase as a separate job, not at app startup. Run it in batches, recording success or failure per tenant. Use expand → migrate → contract, because for a while some tenants are on the new schema and some on the old, and the code must work with both. One failed tenant is recorded and alerted on, and doesn't stop the others.

Practice (10 min)

Review this bean

@Bean
DataSource dataSource(TenantRegistry registry) {
    HikariConfig cfg = new HikariConfig();
    cfg.setJdbcUrl("jdbc:postgresql://pg-shared-1/app");
    cfg.setConnectionInitSql("SET search_path TO "
        + registry.schemaFor(TenantContext.current().orElse("public")));
    return new HikariDataSource(cfg);
}
Worked answer
  1. Init SQL runs once per physical connection, so tenants are never switched.
  2. The bean is built at startup, where there is no tenant. So every connection gets public (or whatever schemaFor("public") returns): a default tenant.
  3. String concatenation into SQL.

Fix: a plain pool wrapped by TenantSchemaDataSource, using require(), a registry-validated schema, and set_config with a parameter.
