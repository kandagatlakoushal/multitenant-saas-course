Noisy neighbours

 IN.ACME   -┐
 IN.HOOLI  -┼-> [ingester: listener per tenant, rate limit per tenant] -> shards -> parsers
 IN.GLOBEX -┘        slowing ONE listener only grows THAT tenant's own queue
ControlWhere
QuotaControl plane: messages per day, per tier. Enforced at the ingester.
Rate limitA token bucket per tenant on the ingester listener and the BFF. Source queues give free back-pressure.
BulkheadListener containers per shard or dedicated tenant, executors per tier.
Load sheddingReject early and cheaply (429/503), lowest tier first. Retries must back off.
TieringThe structural fix: dedicated queue, own database.

Observability per tenant

  • Put tenantId in the MDC where you set TenantContext, and remove it in the same finally. MDC is a ThreadLocal too.
  • Cardinality: series = metrics × tenants × other tags × buckets. 40 timers × 300 tenants × 5 stages × 30 buckets is about 1.8 million series. 6 key metrics × 300 × 5 is 9,000.
  • Put the tenant tag on a few key metrics only (messages, errors, DLQ depth, lag), and enforce that with one MeterFilter allow-list.
  • Per-tenant alerts on error ratio, DLQ depth and lag. A global average hides one small tenant's total outage.

Lifecycle

 ONBOARD:  registry PROVISIONING -> schema + full migration -> queues/authz -> config/users
           -> ACTIVE -> smoke test with a synthetic message
 OFFBOARD: SUSPEND (ingestion + login) -> drain -> export -> retention -> delete everything
           (schema/DB, caches, queues, DLQ, per-retention logs) -> tombstone; NEVER reuse the ID

Making a tenant ACTIVE before its schema exists recreates the "missing schema falls back to public" leak. Backups hold the data until they expire: document it. Azure: Tenant lifecycle.
