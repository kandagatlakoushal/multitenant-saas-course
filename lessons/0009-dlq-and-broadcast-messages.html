The DLQ and broadcast messages

The fail-closed path

 listener throws (unknown tenant / parse error)
   -> session rollback -> RedeliveryPolicy: retry with delay, up to maximumRedeliveries
   -> exceeded: "poison ack" -> broker moves message to the DLQ (properties kept, incl. tenantId)
  • RedeliveryPolicy lives on the connection factory, and can be set per destination with a RedeliveryPolicyMap. Default maximumRedeliveries is 6 and initialRedeliveryDelay is 1000 ms ⚠ verify for your version.
  • The default DLQ is a single shared ActiveMQ.DLQ. individualDeadLetterStrategy with queuePrefix="DLQ." gives one DLQ per destination.
  • The broker adds a dlqDeliveryFailureCause property to dead-lettered messages.
  • Unknown tenant: retry a few times (that covers a registry reload race after onboarding), then DLQ and alert.

ActiveMQ Classic docs: Redelivery Policy; Message Redelivery and DLQ Handling.

Per-tenant triage

  • Metric: DLQ depth by tenant (unknown when there's none), alerted per tenant.
  • Browse with a selector: tenantId = 'hooli'.
  • Replay tool: keeps the original tenantId and re-validates it, sends to the tenant's current destination, rate-limited. Messages with no tenant are never replayed blindly.

Broadcast messages

 VirtualTopic.RATES_PUBLISHED (scope=GLOBAL, allow-listed, no tenantId)
   consumer: for t in registry.active():  set(t); try apply(t) catch record(t) finally clear()
   or producer: one message PER TENANT with tenantId -> normal path, normal DLQ

"No tenant" means broadcast only on allow-listed destinations. Everywhere else it still fails closed. Use one transaction per tenant, and one tenant's failure doesn't stop the rest.

Practice (10 min): the hooli incident

At 09:10, hooli starts sending trades with a malformed date. By 09:40, ActiveMQ.DLQ holds 48,000 hooli messages plus about 30 from others (some with no tenant). Hooli fixes their side at 10:15 and asks you to "reprocess everything". Write your plan: detection, containment, separation, replay, and what to change next time.

Worked answer
  • Detect: the per-tenant DLQ alert fires, and dlqDeliveryFailureCause confirms one cause.
  • Contain: pause hooli's ingester endpoint, so messages wait on IN.HOOLI in order. Note that each bad message burned 6 redeliveries on a shared shard: a noisy neighbour.
  • Separate: move hooli's messages to DLQ.HOOLI.PARK with a selector. Investigate the no-tenant messages separately: they are a lost-context bug.
  • Replay: the parked messages are still malformed. Prefer hooli re-sending the 09:10–10:15 window. Otherwise, use a reviewed transformation. Keep the original tenantId, use the current destination, rate-limit, and replay before resuming new traffic so older events don't overwrite newer ones.
  • Next time: fewer retries for parse errors (per-destination policy), per-tenant DLQs, and a replay tool that enforces these rules.
