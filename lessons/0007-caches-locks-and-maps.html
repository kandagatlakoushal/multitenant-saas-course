Caches, locks and maps are data too

Your win: review in-memory state and find every key that is missing the tenant.

Recall first (2 min)

  1. What does connectionInitSql get wrong for multi-tenancy?
  2. What is wrong with a @Transactional method that loops over tenants?
Check
  1. It runs once per physical connection, not per borrow. (Lesson 6)
  2. One transaction borrows one connection with one path, so every write goes to the first tenant. (Lesson 5)

The rule

Any in-memory structure that holds tenant data is a shared table with no WHERE clause, unless its key includes the tenant: a tenant-scoped key.

 key (table, version)                  key (tenant, table, version)
 ("instruments", 42) -> acme's rows     ("acme",  "instruments", 42) -> acme's rows
 hooli asks ("instruments", 42)         ("hooli", "instruments", 42) -> hooli's rows
   -> gets ACME's rows   LEAK

A real-world style leak: versions are counters per tenant, so acme and hooli both reach version 42. Whoever loads first fills the cache for both. There is no error, just wrong reference data driving rules and reports, and only when two version numbers collide.

Spring @Cacheable: the default key is built from the method parameters only, and the tenant isn't a parameter. Spring: Cache annotations, default key generation.

@Bean
KeyGenerator tenantKeyGenerator() {
    return (target, method, params) ->
        new TenantKey(TenantContext.require(), method.getName(), List.of(params));
}
// @Cacheable(cacheNames = "refdata", keyGenerator = "tenantKeyGenerator")

Key everything by tenant

  • Caches (Caffeine, @Cacheable, Redis prefixes).
  • Static and singleton maps, memoised lookups.
  • Locks (ShedLock names, synchronized on interned strings).
  • Rate-limit counters, and idempotency or de-duplication stores (tradeId repeats across tenants).
  • Eviction must be possible per tenant, for offboarding and data corrections.

Practice (12 min): review three snippets

// A
record RefKey(String table, long version) {}
List<Row> rows(String table, long v) { return cache.get(new RefKey(table, v), k -> repo.load(k.table(), k.version())); }

// B
@Transactional public void rollupAll(List<String> ids) {
    for (String t : ids) { TenantContext.set(t); try { summaryRepo.save(...); } finally { TenantContext.clear(); } }
}

// C
private static final Map<String, String> LEI_BY_CODE = new ConcurrentHashMap<>();
String lei(String code) { return LEI_BY_CODE.computeIfAbsent(code, c -> jdbc.queryForObject("select lei ...", String.class, c)); }
Worked answer
  • A: the key lacks the tenant. Fix: RefKey(tenantId, table, version) using require(). Size the cache for tenants × entries, or one tenant evicts everyone else's.
  • B: one transaction, one connection, one path, so every summary is written to the caller's tenant, or the whole thing fails closed if none is set. Fix: no transaction on the loop, a @Transactional per-tenant method on another bean, and one tenant's failure doesn't stop the others.
  • C: counterparty codes are per tenant, and the first tenant's answer serves everyone for the life of the JVM. Fix: key by (tenantId, code), a bounded instance cache, not a static.
