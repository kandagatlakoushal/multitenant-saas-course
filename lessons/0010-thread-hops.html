Where the ThreadLocal is lost

 listener thread [tenant=acme]
   |- @Async                        -> task executor      [?]  lost / stale
   |- executor.submit(...)          -> pool thread        [?]  lost / stale
   |- CompletableFuture.supplyAsync -> common pool        [?]  lost
   |- parallelStream()              -> common pool        [?]  sometimes
   |- cache refreshAfterWrite       -> cache executor     [?]  lost
   |- publishOn / subscribeOn       -> Reactor scheduler  [?]  lost
   (@Scheduled tick: a boundary with NO tenant at all)

"Stale" is worse than lost. A pooled worker keeps whatever tenant was last set on it. Propagation always means: capture, set, run, then clear in finally.

Three fixes

1. TaskDecorator (executors and @Async)

public Runnable decorate(Runnable task) {
    String captured = TenantContext.current().orElse(null);        // on the submitting thread
    return () -> {
        String previous = TenantContext.current().orElse(null);    // non-null only if run on the caller
        TenantContext.clear();                                      // never trust a pooled worker
        try { if (captured != null) TenantContext.set(captured); task.run(); }
        finally { TenantContext.clear(); if (previous != null) TenantContext.set(previous); }
    };
}

Boot applies a TaskDecorator bean to its auto-configured executor ⚠ verify for your Boot version. Executors you build yourself need setTaskDecorator. A bare Executors.newFixedThreadPool gets nothing. Spring: Task Execution and Scheduling.

2. Micrometer context propagation

ContextRegistry.getInstance().registerThreadLocalAccessor("tenantId",
    () -> TenantContext.current().orElse(null), TenantContext::set, TenantContext::clear);
// then: new ContextPropagatingTaskDecorator()   (Spring 6.1+), or ContextExecutorService.wrap(executor)

Micrometer Context Propagation.

3. Reactor

Write the tenant into the Reactor Context with .contextWrite(Context.of("tenantId", TenantContext.require())). Turn on automatic propagation (Hooks.enableAutomaticContextPropagation(), Reactor 3.5.3+) so the registered ThreadLocal is restored around operators. Reactor reference: context propagation.

Rules: always pass an executor to CompletableFuture. Avoid parallelStream(). InheritableThreadLocal copies only when a thread is created, so it doesn't help with pools. @Scheduled jobs loop over tenants explicitly. Cache loaders set the context from the key.

Practice (12 min)

The cache-reloading scheduler

@Scheduled(fixedDelay = 600_000)
void reload() { byIsin = ratingsRepo.findAll().stream().collect(toMap(Rating::isin, r -> r)); }
Rating get(String isin) { return byIsin.get(isin); }

What happens (a) with our fail-closed data source, and (b) with a "default schema" added? How would you rewrite it?

Worked answer

(a) No tenant on the scheduler thread, so require() throws on every reload. The map stays empty forever: no leak, but a silent outage. (b) One schema's ratings are served to every tenant, with no errors. Both versions also key by ISIN only.

Rewrite: a map of tenant → (isin → rating). reload() loops over active tenants, setting and clearing the context for each, keeps a tenant's old entry if its reload fails, and drops offboarded tenants. get looks up TenantContext.require() first.
