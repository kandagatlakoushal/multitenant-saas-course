Silo, pool, bridge: decided per layer

Your win: describe any tenant's placement as three answers (compute, queues, database), name the overall model, and name the risk it accepts.

Recall first (2 min)

From your own platform, before reading on. Write the answers down.

  1. How does one of your services "know" which customer it serves today? Name two places that knowledge lives.
  2. What happens to a ThreadLocal set on a pooled thread that is never removed?
Check
  1. Usually the active Spring profile, a customer-specific application-<customer>.yml, the JDBC URL of that customer's database, queue names in config, or deployment environment variables. In a shared deployment, every one of these becomes a per-tenant lookup.
  2. The next task on that thread sees the old value. In this course, that means it runs as the previous tenant: a cross-tenant leak.

Why providers share at all

 PER-CUSTOMER (today)                     SHARED (target)
 Customer A: [50 svcs][queues][DBs]       +----------------------------+
 Customer B: [50 svcs][queues][DBs]  ==>  | 50 svcs, one deployment    |
 ...                                      | shard queues + some silos  |
 Customer K: [50 svcs][queues][DBs]       | shared DB(s), schema/tenant|
                                          +----------------------------+
 cost ~ K stacks · onboarding = a stack    cost ~ 1 stack · onboarding = registry entry
 release = K rollouts                      release = 1 rollout, 1 version

Sharing buys lower cost, onboarding in minutes, and one release. In return the provider accepts a bigger blast radius, the risk of cross-tenant leaks, and noisy neighbours. Sources: AWS SaaS Architecture Fundamentals; Azure multitenant guide.

Meeting line: "Sharing trades isolation by construction for isolation by enforcement. Our job is to make the enforcement impossible to forget."

Three models, chosen per layer

ModelMeaningIn our pipeline
SiloDedicated to one tenantglobex has its own database and its own PARSE.globex queue
PoolShared by many tenantsacme and 40 others share PARSE.shard-0..3 and the parser pods
BridgeA mix across layersPooled compute and queues, but a siloed schema per tenant
            compute     queues               database
 acme       POOL        POOL (shard-2)       schema on pooled server   -> bridge
 globex     POOL        SILO (dedicated)     SILO: own DB              -> bridge, top tier
 hooli      POOL        POOL (shard-1)       POOL: shared tables       -> pool
 initech    SILO        SILO                 SILO                      -> legacy silo

Two key points. The model is chosen per layer, so "are we silo or pool?" is the wrong question. And it can differ per tenant: that is tiering, and it is why the tenant registry holds a placement for each tenant. AWS Fundamentals; Azure Tenancy models (which says "vertically/horizontally partitioned" for the same ideas).

Isolation is not the same as silo. Isolation must be enforced and tested in every model. A silo still leaks if code connects to the wrong database. A pool can be well isolated with row-level security. AWS Tenant Isolation Strategies.

Control plane vs application plane

The control plane manages tenants: the registry, onboarding, offboarding and per-tenant config. The application plane (ingester, parser, enricher, rules, reporter) does the tenant's work. It reads the registry and never decides who the tenants are. Validate the registry at load time: a duplicate id or sourceQueue is a leak waiting to happen.
