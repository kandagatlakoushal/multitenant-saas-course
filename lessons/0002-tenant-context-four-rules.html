Tenant context: the four rules

Your win: trace a message through the pipeline and point at every place where the tenant identity is lost, taken from an untrusted source, or guessed.

Recall first (2 min)

  1. Describe acme's placement as three per-layer answers. What is the overall model?
  2. Name one control-plane and one application-plane component in our pipeline.
Check
  1. Compute pool, queues pool (shard), database schema on a pooled server: bridge. (Lesson 1)
  2. Control plane: registry, onboarding, offboarding, per-tenant config. Application plane: ingester, parser, enricher, rules, reporter.

The four rules

  TRUSTED EDGE             PROPAGATION                         USE
  (assign once)            (pass on, never re-derive)

  IN.ACME --> INGESTER --JMS prop tenantId=acme--> PARSER --JMS--> ENRICHER --REST--> REFDATA
             registry:                               |                   X-Tenant-Id: acme
             queue -> tenant                 boundary: set / finally clear
                                                     |
                                          ThreadLocal TenantContext
                                          -> DB borrow, cache keys, outbound copies
  1. Assign once, at the trusted edge. The ingester takes the tenant only from the queue the message arrived on, because you control which credentials can write to IN.ACME. A tenantId inside the message is customer-controlled: overwrite it.
  2. Pass it on, never re-derive it. Use the JMS property tenantId between services and the header X-Tenant-Id on internal REST calls. Don't recompute it from an account number. Business keys repeat across tenants.
  3. Hold it in a ThreadLocal. Set it at the boundary and clear it in finally. Listener and servlet threads are pooled.
  4. Fail closed, with no default tenant. A missing or unknown tenant means throw, roll back, redeliver, then dead-letter queue (DLQ).

JMS property names must be valid Java identifiers (JMS specification, Message Properties). tenantId is legal; X-Tenant-Id is not.

The code

public final class TenantContext {
    private static final ThreadLocal<String> CURRENT = new ThreadLocal<>();
    public static void set(String id) {
        if (id == null || id.isBlank()) throw new MissingTenantException();
        String existing = CURRENT.get();
        if (existing != null && !existing.equals(id))      // previous task didn't clear: loud, not silent
            throw new IllegalStateException("Tenant already set to " + existing);
        CURRENT.set(id);
    }
    public static String require() {
        String t = CURRENT.get();
        if (t == null) throw new MissingTenantException();
        return t;
    }
    public static Optional<String> current() { return Optional.ofNullable(CURRENT.get()); }
    public static void clear() { CURRENT.remove(); }        // remove(), not set(null)
}

@JmsListener(destination = "PARSE.shard-${parser.shard}")
public void onMessage(Message m) throws JMSException {
    String tenantId = m.getStringProperty("tenantId");
    registry.requireKnown(tenantId);                       // null/unknown -> throw -> redelivery -> DLQ
    TenantContext.set(tenantId);
    try { parser.handle(m); }
    finally { TenantContext.clear(); }
}

// Every outbound send copies it:
jmsTemplate.convertAndSend(dest, payload, msg -> {
    msg.setStringProperty("tenantId", TenantContext.require());
    return msg;
});

The ingester binds the tenant to the endpoint, not to the message. It registers one listener per registry entry with JmsListenerConfigurer, and passes the tenant ID from the registry into the handler. Whether a thrown exception actually causes redelivery depends on sessionTransacted on your listener container ⚠ verify for your Boot version.

Practice (12 min): find the leaks

Read this five-service sketch. Mark every point where identity is lost, comes from an untrusted source, or is guessed. Write your list, then check.

[1] INGESTER  @JmsListener(destination = "IN.ALL")                    // one queue for all customers
              t = m.getStringProperty("tenantId");                      // sent by the customer
              jms.convertAndSend("PARSE.shard-" + shard(t), body(m));   // no post-processor
[2] PARSER    set(m.tenantId) ... convertAndSend("ENRICH", tr, copyTenant()) ... finally clear()
[3] ENRICHER  RestTemplate rt = new RestTemplate();                     // interceptor is on the builder bean
              rt.getForObject(refUrl + "/instruments/" + isin, Ref.class);
[4] RULES     t = accounts.ownerTenantOf(trade.accountNo()); set(t);
[5] REPORTER  t = Optional.ofNullable(m.tenantId).orElse("default"); set(t);
Worked answer
  • [1] Wrong edge. A shared inbound queue no longer identifies the customer, and the code trusts a customer-sent property. Any customer can inject trades into another tenant. Fix: per-customer source queues, tenant from the registry, overwrite any incoming property.
  • [1] Not copied. The send has no post-processor, so the parser receives no tenant.
  • [3] Not copied. new RestTemplate() bypasses the builder's interceptors, so no X-Tenant-Id is sent. (Lesson 10.)
  • [4] Re-derived. Account numbers are not unique across tenants, so this fails intermittently and depends on the data.
  • [5] Default tenant. Lost context silently lands in one tenant's reports.

The pattern: identity is lost when it is not copied, taken from an untrusted source, or recomputed or defaulted.
