Choosing a data approach

Your win: pick database per tenant, schema per tenant, or shared tables with row-level security (RLS) for a tenant profile, and defend it on three dimensions.

Recall first (3 min): Day 1, spaced

  1. Why is "schema per tenant on a shared server" not a pure silo?
  2. Where does @ConditionalOnProperty work, and where is it ignored?
  3. Why must there be no default tenant?
Check
  1. The schema is dedicated, but the server's CPU, I/O, write-ahead log (WAL) and connection limit are shared.
  2. It works on component classes and @Bean methods. It is ignored on other methods, such as @JmsListener methods.
  3. A default turns a visible "missing tenant" bug into silent cross-tenant data.

RLS: isolation enforced by the database

ALTER TABLE trades ENABLE ROW LEVEL SECURITY;
ALTER TABLE trades FORCE ROW LEVEL SECURITY;          -- apply to the table owner too
CREATE POLICY tenant_isolation ON trades
  USING      (tenant_id = current_setting('app.tenant_id', true))
  WITH CHECK (tenant_id = current_setting('app.tenant_id', true));
  • Superusers and BYPASSRLS roles always bypass it. The table owner bypasses it too, unless you use FORCE. Never connect the app as the owner.
  • current_setting(..., true) returns NULL when the setting is missing. tenant_id = NULL is never true, so no rows are returned: fail closed.

PostgreSQL: Row Security Policies.

Meeting line: "Shared tables without RLS put isolation in every query. Schema per tenant puts it in one place, the borrow. RLS puts it in the database."

Practice (10 min)

Choose and justify (write three reasons for each, then check)

  1. Globex: 40% of volume; the contract requires a point-in-time restore of their data within 4 hours; auditors want separate storage.
  2. The long tail: 280 small tenants, self-service sign-up next year, low price point.
  3. Regional banks: 25 steady tenants who want exports on demand and occasional one-tenant data corrections.
Worked answer
  1. Database per tenant on its own server. Point-in-time restore of one server is standard. Separate storage satisfies the auditors. 40% of volume would dominate a shared server. Watch: an extra pool in every service, and a separate line in the migration report.
  2. Shared tables + RLS (or schema per tenant, if switching is already built). Onboarding is a row, not DDL. One migration. Lowest cost. Restore is hard: say so in the contract.
  3. Schema per tenant. pg_dump -n for exports. Corrections stay inside one schema. One server, one pool, 25 migrations.
