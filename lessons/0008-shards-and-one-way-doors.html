Destinations that separate traffic

 SHARED (pool tier)                              DEDICATED (silo tier)
 VirtualTopic.TRADE_PARSED.shard-0..3            VirtualTopic.TRADE_PARSED.globex
   -> Consumer.enricher.VirtualTopic.TRADE_PARSED.shard-2
   -> Consumer.reporter.VirtualTopic.TRADE_PARSED.shard-2

One destination(stage, tenantId) function, used by every producer, picks shard-k or the dedicated queue from the registry. Avoid one queue with a selector per tenant: it is hard to scale and to monitor. ActiveMQ Classic docs: Virtual Destinations.

Sharding: floorMod(hashCode, N)

  • String.hashCode() is specified in its javadoc, so it is identical on every JVM. Never use identity hashes.
  • It can be negative. Java's % keeps the sign, so use Math.floorMod(h, N).
  • Math.abs(h) % N is wrong twice: Math.abs(Integer.MIN_VALUE) is still negative, and for other negative hashes it disagrees with floorMod.

Try N = 4 and N = 5, and look at the red cells and the "moves?" column.

Why N is a one-way door

 N=4: acme -> shard-2   | deploy N=5 |  acme -> shard-1
 shard-2 still holds 10k acme messages;  new ones land on shard-1
 consumers on BOTH process acme at once -> per-account order broken

With mod N, going to N+1 moves about N/(N+1) of keys. Message groups order only within one queue, so moving a tenant means draining its old shard first. Alternatives: consistent hashing or jump consistent hash (only about 1/(N+1) of keys move), or store the shard in the registry at onboarding and never recompute it.

Message groups in a shared queue

m.setStringProperty("JMSXGroupID", tenantId + ":" + trade.accountNo());   // not just accountNo

The broker sends a group to one consumer at a time. Using only accountNo couples tenants that share account numbers. Using only tenantId serialises a whole big tenant. ActiveMQ Classic docs: Message Groups.
